# 小文智能语音助手 · 答辩演讲稿

老师、同学们，大家好！我是刘汉文。今天我汇报的项目是**小文智能语音助手**。

---

## 一、项目简介

本项目面向个人桌面场景，实现了一款 ** Web 端智能语音助手**：打开浏览器即可使用，支持**文字与语音**两种自然交互方式，上手简单、操作便捷。

在设计上，我以**统一意图路由**为主线，把 AI 多轮对话、实时天气查询等能力串联成一套完整体验。技术架构采用前后端分离：**前端**基于 React 19 与 Vite，完成组件化开发与高效构建，并深度集成浏览器原生能力，承担语音识别、定位、划词、音频播放等交互；**后端**基于 Python Flask 提供 RESTful 接口，通过集中式意图解析函数 `parse_command` 统一分发业务，并对接阿里云百炼、高德地图、讯飞语音等第三方服务。界面中还设计了可交互的**「小文机器人」桌面吉祥物**，用 SVG 与动效强化品牌记忆，让助手不只是一块功能面板,更是有温度的交互伙伴。

接下来，我将从**项目总览、系统架构、核心运行流程、核心功能**四个方面展开介绍。

---

## 二、项目总览

本项目定位为**轻量化 Web 桌面智能语音助手**，整体业务逻辑清晰、路径统一：用户通过文字或语音发出自然语言指令；后端由 **`parse_command`** 完成解析与意图识别，再调度到具体业务能力；前后端以 **RESTful API + JSON** 交互，形成「指令下发 → 逻辑处理 → 结果回传」的闭环。整体架构简洁，适合浏览器端的轻量使用场景。

---

## 三、系统整体架构

系统采用分层设计，自上而下分为**表现层、接入层、业务编排层、服务层**，职责清晰、模块解耦，便于维护与扩展。

**表现层**负责用户交互与信息采集：依托 React 组件化组织界面，调用 Web Speech API 等浏览器能力，实现语音采集、音频播放、定位、划词等；并通过 **`XiaowenBot`** 吉祥物，在页面一角提供可拖拽、带表情与轻量动效的视觉锚点，与产品名「小文」形成统一认知。

**接入层**作为统一接口网关，对外提供标准化 RESTful 接口，以 JSON 接收请求、返回响应，保障前后端通信稳定。

**业务编排层**是系统调度中心，以 `task_parser` 中的 **`parse_command`** 为核心，解析自然语言、识别天气、音乐、对话等场景意图，并完成业务分发。

**服务层**为上层提供能力支撑：一方面封装讯飞语音识别、语音合成等语音服务；另一方面集成 DashScope（阿里云百炼）、高德地图、DeepSeek 等，补齐对话、位置与天气等能力。

四层协同，形成完整的**请求—解析—调度—响应**闭环。

下面请大家看**第一张整体架构示意图**。图中体现的是业界常见的「分层 + 能力解耦」思路，可与本项目一一对应：

- **左侧主链路**：浏览器界面 → 统一 HTTP 入口 → Flask 应用 → `parse_command` 完成业务决策；
- **数据持久化**：采用轻量方案——前端用 **sessionStorage** 保存多轮对话上下文，后端用 **JSON 配置文件** 维护本机应用白名单等，而非一开始就上重型云数据库；
- **右侧异步与外部服务**：文生图等耗时任务由后端下发 **taskId**，前端**轮询**取结果；地图、大模型、语音合成等则对应图中的外部服务调用。

这样对照示意图，就能把「课堂上的标准架构」与「本项目的具体落地」讲清楚。

## 四、整体运行交互流程

结合架构图，整条链路从用户发出指令到小文给出回复，可分为四步：**前端采集 → 请求转发 → 后端解析 → 结果回显**。

**（1）指令采集**  
支持文字与语音两种方式。文字模式下用户直接输入；语音模式基于浏览器 **Web Speech API**，并区分普通识别与唤醒模式——开启唤醒后，系统持续监听「小文」或「小文小文」，识别到唤醒词再进入指令聆听。无论哪种方式，指令均由前端 **`CommandInput`** 组件接收。

**（2）请求转发**  
指令进入根组件 **`App.autoSendTask`**：完成参数校验与封装，携带 **task**、对话历史 **history**、可选定位 **location**，通过 **POST** 请求 **`/api/send-task`** 发往后端。

**（3）后端解析**  
请求首先由 **`routes/api.py`** 中的 **`send_task`** 接收。后端模块划分简要说明如下：**task_parser** 是意图解析与业务调度的核心；**routes** 负责 HTTP 接入；**services** 封装讯飞等语音能力；**config** 统一管理密钥与参数，密钥仅存于服务端 **`.env`**，避免泄露。

随后进入 **`parse_command`**：对用户指令做预处理（去空格、统一大小写、拆分关键词等），再按 **Python 顺序优先级 if 分支** 匹配意图，执行天气、音乐、对话等对应逻辑。

**（4）结果回显**  
后端返回 JSON，包含 **`reply`**（主回复）、**`type`**（业务类型），以及天气、图表、音乐链接等扩展字段。前端仍在 **`autoSendTask`** 中解析：先根据 **`code`** 判断成功与否，再依据 **`type`**、**`extraData`**、**`chartData`**、**`previewUrl`**、**`taskId`** 等，通过 **`setContentType`** 切换聊天、天气、音乐、图表、图片等面板。  
补充说明：**本地图片分析**走独立接口与 **`analyzeLocalImage`** 流程，与主指令链路并列，答辩时可现场区分演示。

以上即完整的交互闭环。

## 五、核心功能及实现

以下各项均从**业务目标、代码位置、关键技术**三方面说明，便于对照演示与源码。

### 5.1 AI 多轮对话

**业务**：以阿里云百炼（DashScope）为主模型、DeepSeek 为备用，并实现**自动降级**——主通道异常时切换备用，保障服务连续。

**实现**：大模型调用集中在 **`backend/logic/task_parser.py`**，经 **`openai_compat_chat_fallback`** 封装，以 HTTP 访问兼容 **OpenAI Chat Completions** 的接口（**messages + JSON**），按配置在百炼与 DeepSeek 间尝试。自然语言总入口仍是 **`parse_command`**：未命中天气、音乐、图表等更高优先级分支时，进入默认对话分支，将归一化后的历史拼入消息列表再调模型；内部字段 **`msg`** 在 **`routes/api.py` 的 `send_task`** 中映射为前端 **`reply`**。

**多轮记忆**：前端 **`App.jsx`** 维护 **`chatHistory`**，配合 **`sessionStorage`** 在刷新后临时恢复；请求使用 **`fetch` POST JSON** 至 **`/api/send-task`**，携带 **`task`** 与 **`history`**。技术栈为 **React 状态 + Web Storage + Fetch API**，未引入额外状态库，保持轻量。

### 5.2 实时天气与出行建议

**实现**：仍在 **`parse_command`** 中，先判断 **`"天气" in task`**，并用 **`task_should_skip_weather_branch`** 避免代码讨论等场景误触发。命中后依次调用 **`resolve_weather_city`**、**`get_weather_info`**、**`build_weather_reply`**，将高德 JSON 解析为结构化数据，生成自然语言 **`msg`**，完整结构放入 **`extraData`** 供 **`WeatherCard`** 展示。

**技术**：高德开放平台 REST API，Python 侧用 **`requests.get`** 拉取并解析；定位来自前端 **`fetchClientLocation`**（**Geolocation API**），以 **`location`** 字段上传，后端逆地理以提高「今天天气」等模糊问法命中率。若含旅游、攻略等意图，走 **`is_weather_travel_intent`**：有模型密钥时由 **`compose_weather_travel_plan`** 生成行程，否则 **`weather_travel_fallback`** 模板兜底。

### 5.3 在线音乐检索与播放控制

**后端**：**`parse_music_navigation`** 用正则识别「下一首 / 上一首」，返回 **`music_control`**；点歌走 **`is_music_intent`**、**`search_music_url`**，返回 **`music`** 及 **`previewUrl`**、**`songName`** 等。指代类说法（如「那就听这个吧」）由 **`extract_song_title_from_recent_assistant`** 等从上一轮 **《歌名》** 中抽取关键词。

**前端**：**`autoSendTask`** 按 **`data.type`** 分支——**`music`** 时经 **`useMusicPlayer`**（**`src/hooks/useMusicPlayer.js`**）入队，用 **HTML5 Audio** 播放；**`music_control`** 调用上一首 / 下一首。界面由 **`MusicPlayer`** 展示。前后端仅约定 JSON 字段，前端不再解析自然语言。

### 5.4 数据可视化

**入口一**：话术中命中 **`is_chart_intent`**，由 **`resolve_chart_points_from_task`** 抽取「标签—数值」。  
**入口二**：上传文件，**POST `/api/generate-chart`**，**multipart** 经 **`parse_chart_file`**、**`build_chart_payload`** 生成 **`chartData`**。

**前端**：**`generateChartFromFile`** 使用 **FormData + fetch** 上传，成功后 **`setChartData`** 并将 **`contentType`** 设为 **`chart`**，由 **`ChartPanel`** 以 SVG 渲染；**`workflow`** 来自后端 **`with_workflow`**，用于展示「接收 → 解析 → 出图」步骤。

### 5.5 文生图与图片理解

**文生图（异步）**：后端返回 **`image_pending`** 与 **`taskId`**；前端 **`startImagePolling`** 定时 **GET `/api/image-status/<taskId>`**，经 **`dashscope_poll_image`** 查询百炼任务状态，直至返回 **`imageUrl`** 或失败——典型 **异步任务 + 前端轮询**，避免长时间占用 Flask 连接。

**本地上传分析**：**POST `/api/analyze-image`**，**multipart** 上传 **`image`**、**`question`** 等，由 **`analyze_uploaded_image`** 处理，返回 **`reply` + `workflow`**；肤质等子场景通过 **`kind`** 分流。

### 5.6 本机应用白名单启动

**持久化与校验**（**`backend/logic/user_apps.py`**）：**`load_user_apps` / `save_user_apps`** 读写 **`user_app_launchers.json`**；**`merge_launchers`** 合并内置 **`APP_LAUNCHERS`** 与用户配置；**`validate_exe_path`**、**`validate_display_name`** 校验路径与显示名。

**启动**：经 **`subprocess`** 拉起**已校验的绝对路径**，**不把用户原文拼进 shell**，降低注入风险。图形化选程序可通过 **`pick_exe_dialog.py`** 与 **`/api/user-apps`**、**`DefaultPanel`** 联动。

### 5.7 其他能力

| 能力 | 要点 |
|------|------|
| **划词翻译** | **POST `/api/translate-selection`** → **`translate_selected_text`**，密钥在后端 |
| **朗读 TTS** | **POST `/api/tts`** → **`xfyun_tts`**，**WebSocket** 合成，返回音频流；前端 **Blob + Audio** 播放 |
| **模拟世界** | **`session.WORLD_STATE`**；已在世界中时优先 **`apply_world_action`** |
| **知识库问答** | **`is_knowledge_intent`** → **`ai_answer_with_knowledge`**，检索片段注入 **messages**，可返回 **`knowledgeSources`** |

### 5.8 功能编排小结

上述能力虽多，但遵循同一原则：**`parse_command` 按注释规定的优先级串行匹配**——确定性高的分支在前，通用对话在后；**`routes/api.py`** 只负责取参、调用 logic、拼装 JSON 或二进制，业务判断不堆在路由层。答辩时打开 **`parse_command` 的文档字符串**，即可说明「先匹配什么、后匹配什么」。

## 六、小文桌面吉祥物

在核心能力介绍完之后，再补充一块**界面侧的产品化设计**——**「小文机器人」**。

设计目标不是炫技，而是给用户一个**人格化的视觉焦点**：西装领带造型，**内联 SVG** 绘制；嘴型、眉眼通过 **`XiaowenBot.css`** 切换多种 **mood**（平静、开心、好奇、困倦、惊讶等），并配合定时眨眼，增强「在场感」。

**交互**：支持鼠标拖拽；松手后根据速度计算初速度，用 **`requestAnimationFrame`** 实现惯性滑行与指数衰减，触边反弹；结束后可有滑落、短暂「晕眩」等状态；靠边静置约 5 秒会触发**探头**小彩蛋。位置经 **`localStorage`**（**`xiaowen_bot_pos`**）持久化；**`resize`** 时坐标夹紧在视口内。同时尊重 **`prefers-reduced-motion`**：用户开启「减少动效」时关闭强惯性动画，兼顾无障碍。

代码位于 **`XiaowenBot.jsx`**、**`XiaowenBot.css`**，在 **`App.jsx`** 挂载，与主面板解耦，**不占用后端接口**，纯前端表现层能力，与唤醒词「小文」形成一体体验。

## 七、工程亮点与局限

**亮点**  
1. **单入口、强编排**：`/api/send-task` 集中承接自然语言，前端逻辑不散落。  
2. **安全**：密钥与第三方调用均在服务端，前端只拿业务结果。  
3. **语音**：默认 Web Speech，演示成本低，并预留讯飞听写扩展。  
4. **健壮性**：模型降级、接口失败提示等路径完整，利于稳定演示。

**局限与展望**  
当前以本机前后端联调为主，尚未做生产级集群、消息队列与独立数据库；部分能力依赖外网与第三方配额；语音效果与浏览器环境相关。后续可引入用户体系与数据库、将长耗时任务完全消息化，并加强监控与限流。
